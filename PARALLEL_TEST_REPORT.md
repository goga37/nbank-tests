# Отчёт: внедрение параллельного запуска тестов

## Что было сделано

1. **`src/test/resources/junit-platform.properties`** — включена параллельность JUnit 5:
   ```properties
   junit.jupiter.execution.parallel.enabled=true
   junit.jupiter.execution.parallel.mode.default=concurrent
   junit.jupiter.execution.parallel.config.strategy=fixed
   junit.jupiter.execution.parallel.config.fixed.parallelism=5
   ```
2. **`SessionStorage`** — общее для всех тестов хранилище пользователей обёрнуто в
   `ThreadLocal<SessionStorage>` (`ThreadLocal.withInitial(SessionStorage::new)`), чтобы у каждого
   потока была своя независимая копия и тесты не гонялись за общими данными.
3. **`TimingExtension`** (`common/extensions`) — реализует
   `BeforeTestExecutionCallback`/`AfterTestExecutionCallback`, логирует в консоль имя потока, имя
   теста и его длительность. Подключён к `iteration1.BaseTest`, от которого наследуются как API-,
   так и UI-тесты (`ui.BaseUiTest extends iteration1.BaseTest`), поэтому замеры покрывают весь
   проект.
4. **`.mvn/extensions.xml`** — build-time профайлер Maven
   (`com.soebes.maven.extensions:maven-buildtime-profiler`), который в конце каждой сборки печатает
   время каждой фазы жизненного цикла (`clean`, `compile`, `test` и т.д.) — это и стало источником
   цифр для таблицы ниже.

## Замеры

Полный прогон (`mvn clean test`, 62 теста: API + UI) выполнялся дважды на одной и той же машине,
без изменений в тестах — единственная переменная - конфигурация параллелизма.

| Конфигурация | Кол-во потоков | Время старта (clean+compile+resources) | Время чистого прогона тестов | Общее время выполнения | Результат |
|---|---|---|---|---|---|
| Без параллелизации | 1 | 1.51 с | 50.73 с | 52.43 с | **62/62 passed** |
| С параллелизацией | 5 (fixed) | 1.09 с | 93.05 с | 94.14 с | **54/62** (1 failure + 8 errors) |

*"Время старта" — сумма фаз `clean` + `process-resources` + `compile` + `process-test-resources` +
`test-compile` из вывода Maven Build Time Profiler. "Чистый прогон тестов" — фаза `test`
(surefire). "Общее время" — полное время сборки Maven.*

## Выводы

**Параллелизация не ускорила прогон, а замедлила его почти вдвое и сделала нестабильным.**
Это не общий недостаток подхода, а следствие конкретного узкого места в проекте:

- **API-тесты** параллелятся хорошо: они быстрые, не имеют общего состояния (после введения
  `ThreadLocal` для `SessionStorage`) и упираются только в CPU/сеть.
- **UI-тесты** используют общий внешний ресурс — Selenoid (браузерную ферму с ограниченным числом
  слотов, `-limit 15` в текущей конфигурации). Когда 5 JUnit-потоков одновременно пытаются поднять
  Chrome-сессии, Selenoid не успевает их обслуживать: часть запросов сессий валится по таймауту
  (`SessionNotCreatedException`), а в одном случае реальная браузерная вкладка упала под нагрузкой
  (`WebDriverException: session deleted because of page crash`).
- Поскольку JUnit ждёт каждый упавший тест до истечения таймаута (~90 с на попытку создания сессии)
  перед тем как зафиксировать ошибку, эти простои и утроили общее время прогона — несмотря на то что
  сами тесты, если бы они выполнялись успешно, заняли бы секунды.
- Мы также пробовали поднимать/опускать размер пула потоков JUnit (`fixed=5`,
  `dynamic.factor=4` → ~20-30+ потоков) и отключать VNC/логирование в Selenoid — ни то ни другое не
  изменило картину, что подтверждает: узкое место находится не в JUnit-пуле и не в JVM, а в ёмкости
  внешнего Selenoid-кластера.

**Вывод:** для этого проекта общий параллелизм `fixed=5` на весь набор тестов — неудачная
конфигурация. Правильный следующий шаг — не гонять параллельность вверх/вниз глобально, а
разделить политику: API-тесты параллелить агрессивно (они это позволяют), а UI-тесты либо
исполнять последовательно (`@ResourceLock` на общий ресурс "браузер"), либо ограничить их
параллелизм числом, которое Selenoid реально способен обслуживать одновременно без деградации.

## Исправление: `@ResourceLock` на UI-тестах

В `ui.BaseUiTest` добавлена аннотация:

```java
@ResourceLock(value = "selenoid-browser", mode = ResourceAccessMode.READ_WRITE)
public class BaseUiTest extends BaseTest {
    // ...
}
```

`@ResourceLock` — стандартный механизм JUnit 5 для сериализации доступа к общему внешнему
ресурсу между *независимыми* тестовыми классами (в отличие от `@Execution(SAME_THREAD)`, который
управляет порядком только внутри одного класса). Поскольку аннотация висит на `BaseUiTest`, её
наследуют все UI test-классы (`DepositTest`, `TransferTest`, `ProfileTest`, `LoginUserTest`,
`CreateUserTest`, `CreateAccountTest`) — JUnit гарантирует, что в один момент времени сессию в
Selenoid поднимает только один из них. API-тесты аннотацию не наследуют и продолжают выполняться
в полном параллелизме `fixed=5`.

### Результат после фикса

Три подряд полных прогона `mvn clean test` (62 теста):

| Прогон | Результат | Время `test`-фазы |
|---|---|---|
| 1 | 62/62 passed | 70.4 с |
| 2 | 62/62 passed | 77.4 с |
| 3 | 62/62 passed | не замерялось (контрольный прогон только на предмет стабильности) |

Ноль падений во всех трёх прогонах — раньше при `fixed=5` без лока падало 1 failure + 8 errors из
9 UI-тестов практически каждый раз. Время (~70-78 с) хуже полностью последовательного прогона
(50.7 с), потому что UI-тесты (9 из 62, но самые долгие) теперь исполняются строго по одному, а не
параллельно с API — но это ожидаемая и осознанная плата за стабильность: раньше "быстрый, но
падающий" прогон был бесполезен, а нестабильные тесты в CI хуже, чем медленные, но зелёные.

**Итоговая рекомендация:** оставить `fixed=5` в `junit-platform.properties` (это по-прежнему
корректно ускоряет параллелизуемую часть — API), а конкуренцию за Selenoid убирать точечно через
`@ResourceLock`, а не через глобальные настройки пула потоков.
